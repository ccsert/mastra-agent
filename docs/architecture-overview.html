mastra-agent · 企业 Agent 平台架构

面向业务团队的 Agent 平台：集中控制面管理资源与权限，独立 Runtime 执行 Agent、工作流、知识库检索与受限脚本， 控制台提供 14 个工作页面，并通过 OpenAPI 生成 SDK + iframe 组件向第三方业务系统开放接入。

架构上最重要的一句话

Runtime 没有数据库依赖，也没有数据库凭据。 它只通过 /internal/runtime/* 这组 HTTP 接口与控制面通信，凭据、租约、事件持久化全部由控制面掌握。 这条边界由 dependency-cruiser 规则 runtime-has-no-database-access 在 CI 中强制，是为了让 Runtime 可以单独部署到客户私网。

代码量分布（不含 node_modules 与构建产物）：控制台 32.4k 行 / 201 文件，控制面 12.7k 行 / 79 文件， Runtime 4.0k 行 / 36 文件，共享包 14.9k 行 / 49 文件，测试 11.8k 行 / 55 文件。 另有 apps/agent-ui-example 是原生 JS 的第三方订单工作台示例，不计入 TS 统计。

03端到端数据流

五个最主要的使用路径。下面每一步都对应真实代码路径。

  1. 控制台提交消息
    POST /api/v1/projects/:id/conversations/:cid/runs —— 带 requestId 做幂等。浏览器在响应头之前取消也会保留请求，转而去取消 Run，避免"以为没发出去实际已执行"。
  2. 控制面建立 Run 并冻结发布快照
    校验 agent.run 权限 → 在事务内锁会话行 → 写入 runs（含 release_id、deadline、runtime_id）。唯一索引 one_active_run_per_conversation 阻止同一会话并发运行。
  3. Runtime 认领
    POST /internal/runtime/claim → 控制面 SELECT ... FOR UPDATE SKIP LOCKED，签发 lease_token，置 lease_until = now() + 20s。
  4. 控制面回传执行所需全部材料
    模型配置与凭据、工具定义、Skill 版本、知识库快照、历史消息 —— 凭据在这一步解密后随任务下发，Runtime 全程不访问数据库。
  5. 执行 + 心跳 + 事件上报
    Runtime 建 Mastra Agent 流式执行；每 4s 心跳续租（同时收回 cancelRequested）；每个 chunk 通过 POST .../events 上报，序号严格连续、内容幂等去重。
  6. 控制面转 SSE 给浏览器
    浏览器订阅 .../stream，控制面轮询 run_events 推送。断线重连走 GET 续传，不会重复发 POST。
  7. 收尾
    Runtime POST .../finish 提交终态与助手消息；控制面在锁内复核租约后落库，写入 messages。
  1. 画布草稿 → Mastra 工作流定义
    FlowGram 画布管理草稿与撤销，canvas/ 里的文档转换把画布结构映射为可执行树，后端做拓扑与类型校验。
  2. 发布固定版本
    发布时生成 releases 快照，工具/Agent 版本一并固定。后续改草稿不影响已绑定版本的运行。
  3. 提交运行
    POST /api/v1/projects/:id/workflow-runs 写入 workflow_jobs，同样是幂等 + 唯一约束。
  4. Runtime 工作流泳道认领
    当前只用到 .then() / .branch() / .map() / .commit() 这一档控制流；Mastra 的 parallel / dountil / foreach / sleep / suspend-resume / time travel 均未使用。
  5. 节点执行与逐节点上报
    Agent 节点、工具节点、变量映射节点分别执行，节点级事件写入 workflow_node_runs 与轨迹。
  6. 结论文档落库
    输出写入工作区产物，运行详情页按调用 ID 归并交错的输入输出。
注意

工作流内嵌的 Agent 节点在调用工具时不携带 access.task，因此没有工具收据保护；租约过期重放时存在重复副作用风险。子代理显式剥离了该能力。

  1. 上传文档
    文档先经子进程解析（env: {}、--max-old-space-size=512、stdio 关闭、30s 超时后 SIGKILL），解析器自身还有 ZIP 炸弹与页数上限防护。
  2. 分块
    用 @mastra/rag 的 MDocument 做 chunking，按 Markdown 或纯文本分支处理。
  3. 入库作业
    写入 knowledge_jobs，Runtime 知识库泳道认领，通过控制面发往 /embeddings，维度校验（DIMENSION_MISMATCH）后写入 knowledge_chunks.embedding（pgvector）。
  4. 检索
    查询向量化 → 向量召回 → 若绑定了重排模型则调 /rerank 得到 rerankScore → 返回带来源的命中。
  5. Agent 使用
    Agent 只能检索自己发布快照里绑定的知识库，运行时二次校验，防止越权检索。
  1. 导入 Skill
    支持 ZIP 与 Git 来源。ZIP 解析在解压前和解压中都做体积限制，拒绝符号链接、加密条目、路径穿越（Zip-Slip），做 NFC 与大小写冲突检测。
  2. 固定版本与授权
    内容修改产生新版本；skill_files 记录文件摘要；Agent 发布快照绑定具体版本与脚本授权，包内声明不等于已授权。
  3. 运行时提供指令与资料
    通过 CompositeVersionedSkillSource 提供版本化 Skill，读取权限与当前运行租约绑定；停用版本会取消进行中的流。
  4. 脚本在 Docker 沙箱执行
    镜像必须 digest 固定或本地 sha256:（--pull=never，无宿主回退）；技能内容经只读命名卷挂载，不用宿主绑定路径。
  5. 容器约束
    --user 1000:1000 --network none --read-only --cap-drop ALL --memory 128m --pids-limit 64 no-new-privileges，仅注入 HOME/PYTHONDONTWRITEBYTECODE，不含任何宿主环境变量与凭据。
  6. 超时与清理
    30s 软停、47s 硬 SIGKILL 加 docker rm -f；stdout+stderr 合计上限 64KiB；清理后重新校验容器与卷确实不存在，否则抛 SKILL_CLEANUP_FAILED。
缺口

容器与卷按名字清理，没有按 label 的启动清扫。进程被 SIGKILL（Compose 的 stop_grace_period: 30s 短于 47s 硬超时）会永久残留容器、临时目录与命名卷。

  1. 注册应用
    项目管理员创建应用身份，拿到 accessKey 与一次性下发的 secretKey；密钥加密存储，列表只返回 accessKey。
  2. 签名调用
    请求头 Platform-HMAC <id>:<accessKey>:<sig>，签名 = HMAC-SHA256(secret, method ∥ target ∥ timestamp ∥ nonce ∥ sha256(body))，时间窗 ±5 分钟。
  3. 防重放
    auth_nonces 插入用 ON CONFLICT DO NOTHING RETURNING，重复 nonce 抛 REPLAY_DETECTED；签名比对用 timingSafeEqual。
  4. 能力被收窄
    应用身份被硬编码为「只能访问自己所在的这一个项目」且只有 project.read + agent.run，泄露凭据无法横向移动。
  5. 嵌入业务系统
    通过生成的 OpenAPI SDK 调用，或用 iframe 嵌入页面协作（origin 固定 + postMessage 桥 + 8s 存活探测）。

请求进入控制面的顺序

  1. 结构化日志中间件 —— 记录 X-Request-Id 与状态码
  2. 错误映射 —— 领域错误 → 原样消息；Zod → 400；其余一律泛化 503 INTERNAL_ERROR
  3. 写入保护 —— 非 GET/HEAD/OPTIONS 且带 Origin 时必须命中允许列表，且 Content-Type: application/json
  4. 路径策略门 —— authorizeProjectRequest 按方法 + 子资源映射权限，未分类默认 resource.manage
  5. 路由处理 —— 领域方法内部再调 Access.require 做真实校验
授权是双层的

路径策略门是粗筛，真正的判定在领域方法里的 Access.require（90+ 处调用点）。两层不一致时以领域方法为准 —— 例如 conversation-runs 没被路径策略列出，于是落到 resource.manage，比处理函数实际要求的 project.read 更严。

06Runtime 执行面

入口 main.ts 只做两件事：起一个 /health + /ready 的极简 HTTP 服务，然后启动 runWorker。 worker.ts 用 Promise.all 并行拉起四条泳道。

泳道认领端点做什么
agents/internal/runtime/claimAgent 对话执行，含 durable 恢复、工具收据、子代理委派、网页工作区
workflows/internal/runtime/workflows/claim工作流节点执行与 AI 编排生成
knowledge/internal/runtime/knowledge/claim文档分块、向量入库、检索与重排
mcp/internal/runtime/mcp/claimMCP 能力发现与契约快照
并发模型是垂直的

每条泳道是 while (!signal.aborted) 的顺序循环：认领一个、跑完、再领下一个。没有进程内并发度开关， 只能靠多起几个带不同 RUNTIME_ID 的进程来横向扩展。一个长 Agent 运行会阻塞该进程内其它 Agent 工作。

08租约与可靠性协议

这是整个系统里工程含量最高的部分。所有运行态写入都在事务内复核租约，形成围栏。

一次运行的租约时间线

认领
FOR UPDATE SKIP LOCKED 取一条 runtime_id=$1 AND status='queued' AND deadline>now()（按创建时间排序）
签发
lease_token = randomUUID()，lease_until = now() + 20s，状态置 running
心跳
每 4s 续租 20s，同时回传 cancel_requested
围栏
每次写操作重查 lease_token + status + lease_until + deadline，任一不符即拒绝
取消
心跳发现取消 → 立刻 controller.abort()；任何返回 CANCELLED 的调用也立即中止

事件追加的三个不变量

连续性
seq 必须等于 max(seq)+1，主键 (run_id, seq)
幂等
重传相同 (seq, chunk) 直接返回；内容不同则 EVENT_CONFLICT
预算
seq ≤ 100000，超限或出现空洞都是永久 409 → 运行失败

网络层序号由 Runtime 自己的 seq++ 计数器拥有，并通过 delivery Promise 链串行化， 保证"模型请求捕获"与"流消费"并发发出时不破坏连续性。

崩溃恢复的判定树

条件动作
租约过期，且 recovery_count < 2，且存在 durable 快照，且没有 running 的工具收据重新入队，recovery_count + 1，Runtime 走 registered.recover(...) 续跑
有工具收据仍为 running标记 TOOL_OUTCOME_UNKNOWN —— 拒绝重放结果不确定的副作用
recovery_count 已达 2RUNTIME_LOST

running 且已过 deadlineTIMEOUT
用户已请求取消CANCELLED
恢复是单实例亲和的，不是高可用

reap() 会重新入队但不清空也不改派 runtime_id，而 claim() 按 runtime_id=$1 过滤。 因此被回收的运行只能被同一个 runtime 认领。那个进程如果彻底下线，运行会一直排队到 deadline 再判 TIMEOUT。

10安全边界

已经做对的

  • 凭据加密：AES-256-GCM，每次 12 字节随机 IV，认证标签附加，envelope = base64(iv ∥ tag ∥ ciphertext)。密钥必须是 64 位十六进制，缺失即启动失败。
  • 口令：scrypt + 16 字节随机盐，比对用 timingSafeEqual；未知用户也burn一次哈希，避免用户名枚举。
  • 会话：32 字节随机令牌，数据库只存 SHA-256；cookie httpOnly + SameSite=Strict，12 小时绝对过期。
  • 应用签名：HMAC-SHA256 + 时间窗 + nonce 防重放，签名比对恒定时间。
  • 租户隔离：所有查询带 tenant_id/project_id 谓词，90+ 处 Access.require 覆盖各领域方法；权限每次从数据库重读，撤销即时生效。
  • SQL：全部参数化；游标是 base64url JSON，绑定租户/项目/调用者，跨主体重放会被拒绝。
  • 错误：不向客户端泄漏堆栈，未分类错误一律泛化 503。

需要补的

  • 高 没有改密 / 重置口令路由。认证面只有 status/setup/login/logout/join/me，口令一经设置无法轮换。
  • 高 登录限流是进程内全局数组：20 次 / 60 秒，对所有 /api/v1/auth/* POST 共享。多实例失效，且单个攻击者能打满配额，连带 login/join/logout 一起 DoS。
  • 中 COOKIE_SECURE 默认 false，TLS 部署忘记设就是 cookie 明文传输，且没有启动期拒绝。
  • 中 scrypt 用 Node 默认参数（N=16384），低于当前 OWASP 建议；cost 不写进哈希串，事后无法逐行升级。
  • 中 租户隔离完全靠应用层谓词，没有 Postgres RLS 或 per-request GUC 兜底 —— 漏一个谓词就是跨租户泄露。
  • 中 探针接口存在设计内 SSRF：只挡三个字面量元数据主机名，不挡内网段，可带 Bearer 凭据请求。
  • 中 run_events 只有 10 万条计数上限，没有字节预算，而单条事件体上限 8MiB 且完整请求体会落库。
  • 中 app.onError 返回泛化 503 但什么都不记日志，logger 又刻意不序列化 Error —— 生产环境 503 与数据库错误不可见。

一句话总结

这是一个执行可靠性协议做得相当扎实、架构边界被机器强制的开发里程碑：租约 + 围栏 + 幂等事件 + 工具收据这套东西是真功夫， Runtime 无数据库这条边界让私网部署成为可能。主要风险不在业务逻辑层，而在运维与安全基建那一层 —— 认证轮换、限流、索引、日志、CI、分包点。 项目自己在 README 里标注的「尚未完成企业级生产验收」是准确的。
