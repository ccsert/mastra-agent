# 知识库资料生命周期与制度检索评测

日期：2026-09-13。承接平台管理第 4 阶段，按用户选择优先验证企业制度、流程与权限规则。以下验收资料全部为合成内容，不代表真实企业制度。

## 已实现的使用流程

项目「知识库」现在支持 PDF、DOCX、TXT、Markdown。上传先展示解析正文、来源位置、分段计划和解析限制，用户确认后才创建文档与索引任务。确认只提交预览 ID，索引使用已检查的固定分段，不会在后台重新解析成另一套内容。

每份资料支持更新、版本记录和原文阅读。新版排队、索引或失败期间，旧版继续提供检索；新版索引完整成功后，事务内切换当前检索版本。检索结果携带文档、版本、内容摘要和位置，更新资料不会改变历史结果指向的原文。

知识库检索结果和聊天引用增加「定位原文」，在右侧抽屉阅读固定版本。PDF 按页定位，DOCX/TXT/Markdown 按解析段落定位；跨段落引用会展开整个范围，原样匹配的引用文本高亮。抽屉可切换原文、分段、版本，分段与版本列表分页加载到界面。正文按提取文字展示，并非 PDF 或 Word 原版式画布。

只读成员可进入知识库阅读文档；导入、更新、重试和检索测试需要编辑权限。Agent 的知识使用权继续沿用运行授权，拥有 Agent 运行权不自动获得整份原文阅读权。

## 解析、存储和一致性

- 复用 Mastra `MDocument` 的 Markdown 与 recursive 分段。相邻短段落、短标题章节在大小限制内合并，避免孤立的通用说明占满检索候选；PDF 不跨页合并。
- PDF 使用 PDF.js 文字层；DOCX 使用 Mammoth 提取正文，解析前由 yauzl 检查 ZIP。没有执行文件内脚本或转换不可信 HTML。
- 解析在独立子进程执行，环境变量不从 API 进程继承；最多同时两个解析任务、30 秒超时、512 MiB JavaScript 堆限制。它不是完整的操作系统沙箱。
- 原始文件上限 8 MiB；PDF 最多 200 页；正文最多 20 万字符、文本最多 2,000 段、最多 256 个索引分段。DOCX 最多 1,000 个 ZIP 条目、展开总量 32 MiB，拒绝加密、路径穿越、重复条目与链接。
- migration 18 新增文档版本、预览、当前检索版本指针和 chunk 位置。原始字节、SHA-256、提取正文、段落/页、固定分段计划随版本保存。
- 预览有效期一小时，同一知识库每位操作者最多保留五份。新预览触发该库过期记录清理；没有独立后台清理任务。
- 预览和确认均核对当前项目权限；预览限定原操作者。确认事务检查内容摘要、基准版本和重复请求；过期、他人预览、撤权、跨项目或并发过期版本不能继续导入。
- 新索引分批写入时校验内容与固定计划，进度使用实际已写入数量；成功切换前检查分段完整性。失败/重试清理本次失败索引，保留旧检索版本。
- 当前每个知识库最多 200 份资料、每份最多 30 个版本。历史分段保留并计入原有 10,000 分段容量上限。
- 原 TXT/MD 上传 API 保持兼容。迁移前资料回填 v1，未采集的精确段落位置明确提示为历史缺口。
- 文档和版本目录查询只读取元数据，避免列出版本时加载历史原始文件。原文查询读取指定版本的正文结构与分段。
- 删除文档会取消待执行任务并清除文档各版本的原始字节、正文、分段和预览；已进入历史会话的引用摘录遵循会话保留规则，不宣称同时擦除。

新增 API，统一位于 `/api/v1/projects/{projectId}/knowledge/{kbId}`：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/document-previews` | 解析文件并固定预览 |
| POST | `/document-imports` | 确认预览，创建或更新版本 |
| GET | `/documents/{id}/versions` | 版本元数据 |
| GET | `/documents/{id}/source?versionId=...` | 固定版本正文与位置 |

OpenAPI 和 TypeScript SDK 已生成并通过一致性检查。

## 50 问评测

数据集：[enterprise-policy-v1.json](../evaluations/enterprise-policy-v1.json)。10 份合成制度，50 问：30 个单文档问题、10 个跨文档问题、10 个资料未规定的问题。每个有答案问题提供文档名与必要依据文本，覆盖角色、权限例外、临时访问、导出、发布、回退、采购、审计、规则生效和离岗。

评测通过现有 Runtime 的实际 embedding、vector retrieval 与 rerank 路径执行，使用现有配置的 `qwen3-embedding-4b` 和 `qwen3-reranker-4b`，topK=5。临时数据库 schema 隔离创建，结束时清理；模型凭据不写入报告。

第一轮评测暴露了短章节拆分过细的问题：旧纯文本方案完整依据命中 100%，最初结构分段只有 95%。两个失误都由相同的独立通用说明片段挤占候选造成。已通过合并短章节修复，并在不改问题与标准依据的前提下复测。首次重排运行接近末尾时遭遇模型连接超时；最终脚本增加最多三次临时连接失败重试、逐题保存与中断位置记录，不将未完成题目算作通过。

最终结果见 [评测报告](../evaluations/enterprise-policy-2026-09-13-report.md)，逐题模型返回、来源版本和摘要见 [原始结果](../evaluations/enterprise-policy-2026-09-13-results.json)。数据集、模型标识、topK 和数据集 SHA-256 均记录在结果中。

| 方案 | 完整依据命中（40 问） | MRR | P95 |
| --- | ---: | ---: | ---: |
| 原纯文本分段与向量 | 40/40 | 1.000 | 5,453 ms |
| 来源分段与向量 | 40/40 | 0.988 | 7,749 ms |
| 来源分段、向量与重排 | 40/40 | 1.000 | 10,664 ms |

所有方案在 10 道无答案问题上仍返回了候选。重排组 `cross-4` 曾连接失败，第二次尝试成功，整题 42,547 ms，已经计入耗时统计。上述耗时是一次串行测量，存在模型服务波动，不能直接归因为分段策略的成本差异；本轮没有将重排设为默认。保留来源位置和版本是本轮确定实现的能力收益，检索质量没有证明优于原方案。

这轮测量的是检索依据，未生成最终回答。完整依据命中率仅以 40 个有答案问题为分母；跨文档须全部必要证据命中。无答案问题仍返回片段不等于幻觉率。小型合成数据集不能证明真实企业资料效果，也不能证明重排在大规模语料上的收益。

运行方式：

```sh
pnpm knowledge:eval --embedding-model <现有向量模型ID> --rerank-model <现有重排模型ID> --out .scratch/knowledge-evaluation
```

可通过 `--dataset` 指定相同结构的业务评测集。模型 I/O 发生在现有配置端点；P95 包含端到端检索与发生的重试。未估算模型费用。
