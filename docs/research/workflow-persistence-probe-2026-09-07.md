# Mastra 跨进程恢复与版本固定实验

日期：2026-09-07。对应[持久化事实研究](../../.scratch/agent-platform/issues/24-workflow-persistence-facts.md)。这是可重复的 SDK 实验，未交付平台恢复功能，也未承诺生产 RPO/RTO。

## 结论

Mastra 的持久化工作流可以在新进程恢复挂起任务；平台仍须固定执行定义和实现制品。同 ID 发布覆盖会使旧任务混用新旧版本。外部业务写入与框架检查点不在同一事务中，进程崩溃后的步骤重做需要业务端幂等或结果核对。

Mastra 已有 `resume()` 并发状态占用，本次 libsql 实验中两个进程同时恢复，只有一个成功并产生一次业务写入。不能把这一点扩大成完整租约接管，也不能说框架完全没有并发保护。

## 固定环境与方法

| 项目 | 实际使用 |
| --- | --- |
| SDK | `@mastra/core 1.64.0`、`@mastra/libsql 1.22.3`、`zod 4.5.4`，精确锁文件 |
| 执行环境 | macOS arm64，Node 24.13.0，pnpm 10.32.1 |
| 工作流存储 | libsql 文件数据库；每组夹具独立 |
| 模拟业务系统 | 独立 SQLite 文件账本，Node SQLite 3.50.4；API 为实验状态，仅用作测试夹具 |
| 合成流程 | prepare → approval/suspend → write；崩溃用例省略审批节点 |
| 进程边界 | 8 组数据库夹具，24 个 Node 子进程；不是同进程反复构造 Mastra |
| 故障注入 | 业务事务提交后、工具返回前，父进程向该实验子进程发 SIGKILL |
| 未接入 | 真实模型、真实业务、FlowGram UI、私网连接器、生产数据库与目标 Linux |

## 10 项观察

| 检查 | 实际结果 | 直接含义 |
| --- | --- | --- |
| 检查点内容 | input、节点 payload/output、suspendPayload 含合成订单正文 | 检查点是业务内容存储，不能作为无正文管理状态默认上报 |
| 跨进程挂起/恢复 | 新进程自动加载动态定义并成功 resume；prepare 只执行一次，最终全部 v1 | 基本持久化路径成立；不是保存 JS 调用栈，审批节点重新进入 |
| 终态重复 resume/restart | 成功任务再 resume 报非 suspended；restart 返回已保存成功结果；写入仍为 1 | 不应把 restart 当作“重新跑一个任务” |
| 同 workflow ID 覆盖 v2 | 只剩一份当前定义；旧任务结果为 prepare:v1、approval:v2、write:v2 | 同 ID upsert 不能表达不可变发布版本 |
| workflow/tool 都按版本注册 | 同时保留 orders-v1/orders-v2 与工具版本，旧运行恢复全部 v1 | 不可变执行 ID + 对应实现注册是可行基础 |
| ID 固定但工具代码改变 | 旧结果保留 prepare:v1，后续两个节点使用 changed-code | 单有版本名称不验证实现内容，仍会漂移 |
| 旧工具缺失 | startWorkers 返回后没有装配该流程，getWorkflow 报 not found，写入 0 | 发布就绪需验证所有依赖；启动返回成功不够 |
| 两进程竞争 resume | 同步放行两个进程，1 个成功、1 个收到 already resumed，业务写入 1 | 该引擎/适配器已有状态竞争保护；未证明所有抢占场景 |
| 写入后崩溃，无业务幂等 | 快照 prepare=success/write=running；重启跳过 prepare、再次调用 write，账本 1→2 | 框架恢复不能独自消除外部重复写入 |
| 同窗口崩溃，有业务唯一键 | write 仍调用 2 次，但第二次插入被业务唯一约束消除，账本 1→1 | 幂等必须在实际副作用边界生效，调用次数与业务效果次数不同 |

最后两项的业务 DB 与 Mastra DB 分开，故意保留“业务成功、框架完成状态未保存”的窗口。幂等键在夹具中是 workflow/run/单次写入；这不是平台通用键格式，也没有测试参数改变、并行迭代、远程服务冲突和幂等记录过期。

完整结果：[evidence/latest.json](../../.scratch/agent-platform/research/workflow-persistence/evidence/latest.json)。源码结论及固定提交出处见[发布源码核查](mastra-persistence-source-2026-09-07.md)；其七个关键 npm 源码文件与发布提交逐字一致。

## 对后续发布与恢复契约的具体约束

以下是从实验得到的工程建议；恢复时限、离线政策、版本保留和业务审批有效期仍由相应决策确定。

1. **每次运行绑定不可变发布清单。** 用户看到的流程身份、发布版本与 Mastra 执行 ID 分开。启动后持久化发布 ID、定义摘要、执行 ID、依赖版本/制品摘要和检查点位置；恢复不能重新解析环境的 latest 指针。
2. **固定依赖实现，授权继续实时生效。** 依赖清单覆盖 Agent 配置、工具适配器、子流程、Skill 与脚本环境、模型服务配置和 Runtime 兼容范围。固定配置不表示远端模型/业务服务行为可冻结；远端没有版本能力时应显示限制。Secret 值不入包，轮换与行为版本分开；旧版本不能绕过当前撤销。
3. **发布在依赖验收后切换新任务入口。** 先在目标 Runtime 准备制品、验证摘要和装配完整性，再改变新运行的目标版本。Mastra 的定义 upsert 与多定义顺序保存不替代平台发布事务。旧任务继续引用旧制品；旧制品缺失时报告不可恢复，禁止静默换新版本。
4. **审批与恢复占用分别建模。** 框架的 suspended→running 竞争不替代用户权限、参数摘要、挂起代次、审批有效期或一次性消费记录。`approved: true` 仅用于本实验，公开 API 不得将客户端布尔值直接视为可信批准。
5. **接管前明确执行归属。** source 核查显示 resume 的状态占用不含 owner、租约和 fencing，restart 不走同一占用路径。平台要阻止旧/新执行者同时放行业务调用，不能仅因控制面收不到心跳就重启同一任务。
6. **不确定写入先查证。** 对支持幂等的工具沿用同一业务意图键并校验参数；支持结果查询的先查询。不能确认且不支持幂等的写入进入结果不确定/人工核对，不把超时当作未执行。审批通过不等于允许无限重复写入。
7. **检查点纳入内容政策。** 私有 Runtime 的完整快照留在获准位置，控制面接收经过字段约束的状态投影。临时处理许可不能自动授权完整快照落盘；需要 durable suspend/resume 的流程须有相应内容保存许可或经过验证的受限引用方案。删除恢复所需内容会影响任务可恢复性，应与副本删除状态一起展示。

一次发布清单与运行绑定可以据此细化，但本报告不决定具体数据库、离线授权秒数或客户保留天数。

## 仍需后续验证

- 目标 Linux/Docker、正式持久化适配器及备份恢复；本次本地文件数据库不证明多主机可用性。
- 所有控制流、嵌套运行、并行挂起及多次挂起代次；本次业务流程是线性工具链。
- Runtime 崩溃自动发现、restart 并发、租约与 fencing、连接中断、撤销到期、取消和外部写入对账。
- 审批权限与参数绑定、真实工具/MCP 幂等协议、Agent 内部多轮工具调用与模型输出恢复。
- 持久化事件与会话流恢复、FlowGram 往返及 AI 草稿生成质量。
