# 轨迹增量压缩与会话提问标记 · 交付

接续 `b836145`（已 revert）。该轮按"摘要 + 按需加载"改造轨迹后在真实会话上失败：单轮事件量巨大（实测最大 21,974 条/轮，流式增量逐 token 落库），隐藏明细不可接受，按需加载也缓解不了单轮全量的成本。本轮改为读取侧合并增量，并在会话界面增加提问标记。

## 方案

- 控制面读取侧压缩：连续的 `text-delta` / `reasoning-delta` / `tool-input-delta`（同内容 id、无 observation）合并为单 chunk，拼接文本上限 20,000 字。合并事件保留起始时间、seq 取该段末尾，投影结果（记录、正文、计时）不变，游标分页既不跳过也不重复。轨迹内联前缀与 `listRunEvents` 的 `compact=deltas` 参数均生效；未带参数的原始协议读取保持原样（应用接入页等消费方不受影响）。
- 客户端 tail 分页：带 `compact=deltas`；有 checkpoint 的读取以 seq 边界为准，`batch.length < 500` 的旧启发式仅用于无 checkpoint 的 legacy 读取（合并后每批远小于 500 条）。完整性契约从"数量一致"改为"读到 checkpoint.lastSeq"。
- 会话提问标记：对话界面右侧每条用户消息对应一个短横标记（≥2 条提问时显示），悬停显示"第 N 条提问 + 摘要"，点击平滑滚动到该消息；滚动时高亮当前所在提问。从渲染后的线程 DOM 读取（`data-role="user"`），实时与恢复的消息行为一致；宿主绝对定位覆盖滚动视口。
- 验证后修复了首版的两处错误：sticky 宿主在 flex 内容末尾不会重新进入可视区（改为绝对定位覆盖层），以及压缩后短批次被误判为读取完成。

## 验证（真实会话，8 轮，最大单轮 21,974 条原始事件）

- 轨迹视图完整加载从"数分钟且中途失败"降到 **7 秒**，传输 3.0 MB（改造前 9 秒 4.7 MB 且远未完成）；8 轮全部读取到位，"已加载全部已记录内容"，模型/工具/子代理/计划记录与时间轴完整。
- tail 请求全部携带 `compact=deltas`；单批 500 条原始事件压缩为个位数合并块。
- 会话页 8 条提问对应 8 个标记，悬停气泡显示轮次与摘要，点击跳转后目标消息位于视口顶部。
- `pnpm check` 退出码 0：后端/协议 153 通过、4 跳过（沙箱镜像未配置），Console 170 通过。新增回归：压缩分页继续读到 checkpoint、legacy 无界读取短批终止、集成层确认内联合并与原始游标读取并存。

## 边界

- `data-model-request` 携带完整请求上下文，不做压缩，是剩余传输量的主要来源。
- 导出的协议数据说明已注明"连续增量已合并"；需要逐 token 原文时用未带参数的 `listRunEvents`。
- 标记栏依赖 `data-role="user"` 与 `aui_thread-viewport` 结构（本仓库持有的 assistant-ui 封装），上游结构变化需同步。
