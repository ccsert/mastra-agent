# Agent 应用接入规范草案

> 2026-09-14：第一阶段已实现并通过本地真实模型与浏览器验收。实际交付范围、API 和接入方式以 [SDK 接入指南](../development/agent-application-sdk.md) 为准；本草案中业务写入审批、WebMCP 和浏览器扩展等仍属后续阶段。

状态：设计提案，尚未实现 SDK、公开协议或第三方连接器。日期：2026-09-14。

## 1. 定位

这份规范让 Agent 能在用户授权下操作应用的当前界面，适用于平台自身及第三方应用，不要求使用 React、Ant Design 或特定组件树。应用对外描述页面、业务对象、动作与结果，内部可使用原生 JavaScript、Vue、React、Angular、组件适配器或自己的页面控制器。

[组件适配规范](./agent-ui-component-protocol-2026-09-14.md) 是本规范的一种实现方案。业务动作是对外主接口，组件级读写是可选细粒度能力；两者共用授权和回执。下面的字段、操作名与 SDK 示例均为草案，不代表已有产品 API。

例如第三方订单系统提供 `orders.search`、`orders.open`、`orderDraft.patch`、`orderDraft.validate`，不需要暴露 `AntdTable.rowClick` 或 React props。Agent 能通过同一动作完成页面搜索和定位，不依赖应用采用表格、卡片还是树形布局。

## 2. 应用必须提供什么

| 契约 | 必须表达的内容 |
| --- | --- |
| 应用身份与能力清单 | appId、发布者、协议/能力版本、可信 origin、支持的传输、能力发现入口与授权方式 |
| 连接与页面会话 | connectionId、pageSessionId、页面实例、登录主体关联、当前地址/页面语义、生命周期及用户是否允许操作 |
| 页面观察 | 当前页面摘要、可访问业务对象、活动区域、加载/编辑/阻塞状态、状态 revision、相关动作引用 |
| 动作描述 | 名称、用途、输入/输出 schema、前置条件、真实副作用、可取消性、幂等或对账策略、所需授权 |
| 执行与反馈 | actionId、进度、执行结果、状态变化、实际影响、持久化证据、失败原因、可恢复方式 |
| 用户控制 | 操作中的可见提示、停止/撤销授权、待用户处理的入口；不能仅在 Agent 对话里声称正在控制页面 |

appId 是命名空间，不是凭据。清单内容经连接器登记和来源校验后才能参与发现；应用自报的权限或风险提示不是授权决定。服务端、应用端分别执行各自权限检查。

静态能力清单不能表示已经连接浏览器。页面操作必须绑定具体活动 pageSessionId；同一应用的多个标签页、多个账号和多个租户不能互相串用。页面刷新产生新实例代次，原动作引用失效；恢复需要重新观察和核对，不重放未确认的写入。

## 3. 业务动作与界面状态

动作应描述用户意图，可以一次完成多个内部控件操作，例如“将订单列表筛选为待处理并选中指定订单”。不规定应用如何调用内部组件或 DOM，但要求走应用现有状态和业务处理逻辑。

每个动作声明 effect：read / view / draft / domain。自动保存的编辑属于 domain，即便视觉上只是填入一个字段。domain 动作仍使用该应用的业务授权及必要审阅；草稿操作不能偷偷提交。

每个动作同时声明 executionMode：

- `page`：必须在指定页面会话执行，结果反映到用户正在看的界面。
- `service`：只调用业务服务，不宣称界面已变化。
- `hybrid`：服务动作与页面更新分别给出证据；服务成功而页面失联时，明确报告已保存但未验证页面呈现。

应用可以根据授权提供只读语义区域、业务对象 ID 和分页数据；不要求上传完整 DOM、组件 props 或后台缓存。读取范围、脱敏规则和裁剪情况必须明确。

第三方可以增加自己的业务动作而无须修改平台 enum。通用只读、导航、发现、调用与结果语义统一，具体业务 actionId 和参数 schema 在该应用的命名空间下版本化。完整能力 schema 按需加载，不能因为动作数增加而全部常驻模型上下文。

## 4. 框架无关的交互流程

1. 发现应用及版本，验证连接方式和可信来源；未经连接的页面清单只作为候选应用描述。
2. 建立用户授权的应用连接，再绑定用户指定的页面会话。
3. 获取当前页面状态与相关动作目录，按需读取详细 schema。
4. Agent 使用已发现的动作引用和结构化参数发起请求；可信连接层注入调用主体、任务、应用、页面及授权标识。
5. 应用复核前置条件和 revision，显示操作提示，执行自身 handler 并返回进度。
6. 以页面或服务真实状态确认结果；跨页面导航需确认目标页面会话和状态已就绪。
7. Agent 根据回执继续；遇权限、冲突、页面失联或未知结果时暂停相应动作并核对。

请求示例：

```json
{
  "protocolVersion": "1.0-draft",
  "requestId": "unique-request-id",
  "appId": "example.orders",
  "connectionId": "authorized-connection-ref",
  "pageSessionId": "active-page-ref",
  "action": "orders.search",
  "actionVersion": "1",
  "expectedRevision": "orders-view-17",
  "args": { "status": "pending", "customerId": "customer-42" }
}
```

模型只构造动作与业务参数，不能指定或篡改上面由可信调用层注入的身份和连接字段。schema 根为 object，参数校验与版本校验在执行前完成。

回执示例：

```json
{
  "requestId": "unique-request-id",
  "actionId": "action-93",
  "status": "succeeded",
  "effect": "view",
  "executionMode": "page",
  "view": {
    "pageSessionId": "active-page-ref",
    "revision": "orders-view-18",
    "page": "orders.list",
    "filters": { "status": "pending", "customerId": "customer-42" }
  },
  "result": { "loadedCount": 20, "total": 42, "hasMore": true },
  "evidence": { "uiApplied": true, "persistence": "not-requested" }
}
```

统一支持 accepted、executing、requires-user-action、succeeded、failed、cancelled、unknown。回执附执行时间、结构化错误和重试/对账建议。副作用已经发生但未取得最终回执时必须能进入 unknown；取消并不保证撤销已产生的业务效果。

需要用户处理的结果返回与具体参数摘要绑定的 pendingActionRef 和应用内入口。模型不能通过下一次工具调用代替用户确认自己的请求；参数或目标资源变化后旧确认失效。

## 5. 接入方式与传输映射

| 接入方式 | 适用情况 | 要求 |
| --- | --- | --- |
| 框架无关的页面 SDK/桥接 | 第三方愿意主动接入，用户与 Agent 共享当前页面 | 应用注册观察器与 handler；页面生命周期、取消、提示与回执由 SDK 统一承载 |
| 原生 WebMCP 映射 | 浏览器和应用具备相应能力 | 将同一应用动作注册为 WebMCP 工具；不能因支持 WebMCP 就跳过应用授权和页面绑定 |
| 后端 HTTP/MCP 连接器 + 页面桥接 | 应用同时有成熟业务 API 和可见页面 | service/page/hybrid 三种结果分开；API 成功不自动等于 UI 已更新 |
| 浏览器扩展或本地桥接 | 第三方界面独立打开，平台需要连接其当前标签页 | 用户明确选择应用/页面；桥接关联具体 origin、标签页和用户连接 |
| 可访问性/视觉操作 | 无法改造、未接入的遗留应用 | 作为受控回退，使用同一结果与权限边界；不能承诺与原生接入具有同等确定性 |

WebMCP 当前提供结构化工具、发现、取消及显式跨 origin 暴露机制。它适合作为标准映射，但不会自动建立平台与任意独立浏览器标签页之间的连接。实现应按固定浏览器/协议版本做兼容测试。[官方命令式 API](https://developer.chrome.com/docs/ai/webmcp/imperative-api)

规范定义应用语义，不再另造一套通用消息传输协议：采用 MCP 时映射到协商版本的 tools/resources/结果；采用 WebMCP 时映射到页面工具和生命周期；页面桥接使用版本化消息和明确的连接上下文。所有通道都保留相同 actionId、revision 和审计关联。

若采用 iframe/postMessage 桥接，必须校验精确 origin、source 与握手绑定，拒绝通配来源和来自其他页面的消息；跨窗口或 WebSocket 桥接同样需要短期连接授权和实例代次检查。连接信息不能由模型或应用正文提供后直接信任。

## 6. 身份、权限与跨应用数据

实际允许动作由四项共同决定：平台策略、用户对本次任务的授权、第三方应用授予当前连接的权限、该应用当前用户与资源权限。第三方保持最终业务授权责任，平台管理员不天然拥有第三方管理员权限。

平台到第三方的连接与用户身份映射独立管理。不得把平台 session cookie、平台应用 secret 或平台访问 token 直接转交给第三方；使用面向目标应用的独立授权。采用 MCP HTTP 时按选定版本授权规范校验 token 的目标资源，避免 token 透传。[MCP 授权要求](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

当前 `modules/applications/applications.ts` 的 Platform-HMAC 凭据用于“第三方调用平台”的入站身份，不表示平台已经取得操作该第三方页面的权限。未来可统一管理入口，但入站 API 客户端与出站应用连接必须是可独立授权、撤销和审计的对象。

应用 A 返回的数据进入应用 B 是一次新的跨应用使用，读取授权不等于转交授权。任务授权需标明允许的来源、目的应用和数据范围；凭据及未授权敏感字段不能进入动作参数、模型上下文或轨迹。

第三方动作描述、帮助文字和返回正文只能提供事实与使用信息，不能修改平台系统指令、扩大调用范围或指示将数据发送到未授权应用。

## 7. 给第三方的最小开发包

对外应交付：

- 版本化规范、JSON Schema、能力清单格式及兼容规则。
- 不依赖 UI 框架的 TypeScript/JavaScript SDK，负责注册、连接、观察、执行、取消与结果查询；各框架 hook/组件适配器为可选包。
- 原生 HTML/JavaScript 的参考应用，演示页面搜索、打开业务对象、修改未保存草稿、校验和返回回执。
- WebMCP 与 HTTP/MCP 的映射说明；明确连接用户当前页面与纯后台调用的差别。
- 可替换样式的操作状态/停止 UI，要求语义与交互一致，不强制第三方使用 Ant Design BorderBeam。
- 契约测试与检查工具，能看到当前授权范围、已注册动作、参数 schema、页面状态和真实回执。

SDK 接入体验示意：应用注册 `orders.search` handler，由它调用现有路由/筛选状态，再等待应用数据源完成加载并读回实际结果。业务动作描述稳定，即使应用从 Table 改为卡片列表，Agent 调用方无需跟随更改。

## 8. 对当前实施顺序的调整

第三方接入约束从第一阶段开始落实，不能等全部内部组件包装完成后再反推公共协议。

1. 先实现框架无关核心：应用身份、连接、页面状态、能力发现、执行与回执；平台自身以同样方式注册。
2. 用一个完全不依赖 React/Ant Design 的本地合成第三方应用完成端到端验证，同时迁移平台 Agent 表单作为内部实现对照。
3. 验收同一业务动作在不同页面布局下保持兼容，覆盖两个标签页、账号切换、导航/重载、人工冲突、断线对账及撤销授权。
4. 然后扩展内部组件适配器、第三方 SDK 与标准协议映射。未接入应用的浏览器自动化独立验收。

验收必须证明“用户当前界面确实发生了预期变化”，也必须能准确报告“后台成功，但当前界面未确认”。只有后台 API 测试通过不能算第三方界面接入完成。

本轮仅更新设计文档，未建立第三方连接、发放权限、发布 SDK 或修改运行时代码。
