# 长任务 Agent 与网页迭代验收方案

日期：2026-09-13。本文保留实施前的代码核查与验收计划，表中的“当前代码”为当时基线，不代表后续实现状态。网页工作区、原生持久化恢复、预算、工作记录、只读评审、产物预览和消息编辑分支已接入；当前运行方式与验证边界见 [网页 Agent 运行说明](../operations/web-agent.md)。真实模型的完整 80 步对照实验与获奖质量均未据此确认。

## 目标与优先级

下一阶段让 Agent 在一个持续保存的项目中完成“理解要求 → 修改文件 → 运行网页 → 浏览器验证 → 根据证据修正 → 交付”。前端继续使用 assistant-ui；执行继续以 Mastra 为基础。首个纵向场景选择网页创作，先跑通小闭环，再验证长时间执行。

“可获奖级别”是设计目标，需要人对实际作品判断，自动分数不能证明获奖。70–80 步是执行容量与稳定性目标，不能作为作品质量的替代指标。

本地固定依赖为 `@mastra/core@1.64.0`。以下是安装包公开类型中的能力存在性核查，不等于已经通过本平台集成验收。

## 执行与数据边界

### 任务与执行尝试分开

建议增设 `Task` 保存目标、验收清单、预算、工作区、当前版本和最终候选版本；一个 Task 可关联多个现有 Run/执行尝试。发布快照始终固定。普通问答继续保留现有路径，长任务作为可选执行方式接入，不伪造 80 条用户“继续”消息。

需要持久化的最小状态是：任务需求修订、阶段和清单、原生执行快照引用、工作区版本、预算累计、工具操作凭据、评审结果引用。消息只是对用户展示任务的一个视图。

区分 `executionStatus` 和 `acceptanceStatus`。正常输出、步数耗尽、等待用户、取消、失败和验收通过应有不同含义；最后一步说“完成”不能直接把任务标记为验收成功。

### 持久化与恢复

仓库明确禁止 Runtime 直接访问平台数据库：`.dependency-cruiser.cjs` 的 `runtime-has-no-database-access`。保持控制面拥有平台状态与权限校验，在 Runtime 提供符合 Mastra storage domain 的远程适配，通过内部接口保存需要的快照和线程状态。先实验测量 native durable 实际需要的 storage domains 与事务语义，避免一次性实现整个存储协议。

Mastra 当前公开类型明确说明全局自动恢复会重新发起模型与工具调用，且没有跨实例租约保护。因此由平台 claim/lease 决定唯一执行者，显式调用该 run 的 `recover`；先不打开全局自动恢复。

恢复需要重新装配固定版本的工具和授权上下文，并重新注入取消信号、观察钩子及预算检查。`prepareStep`、部分闭包回调和 signal 不会自然跨进程保存，不能把它们当成持久化状态。

工具采用持久化操作记录：`taskId + attemptId + toolCallId + inputHash`，记录 intent/running/completed/unknown。写文件使用内容版本前置条件，完成后保存内容 hash 和结果；提交检查点只引用已完成的产物。进程在执行后、回执前崩溃时先核对文件/操作记录，无法判断的副作用标为 unknown，不盲目重放。普通构建与只读检查可有限重试，部署等外部写入留待独立能力。

单独延长长任务的服务端预算，保留租约心跳作为存活判断。进程重启不能重置累计步骤、Token、耗时与重试次数。

### 网页工作区

首版选独立 Docker 工作容器与持久卷，不扩张现有短脚本沙箱。预置 Node、锁定依赖和浏览器环境；依赖缓存、资源获取和任务文件分开保存。已有 Skill 包继续只读，Skill 是方法与参考资料，文件和浏览器工具是实际执行能力。

最小工具面：文件读取/搜索/补丁、命令执行及进程状态、启动/停止预览、页面打开与交互、截图、测试报告、文件版本和差异。对持续运行的 dev server 使用进程句柄，不能让单次工具调用永远等待。首版仅授权任务目录、任务预览地址及必要依赖/素材来源，不授予宿主文件或业务凭据。

预览通过隔离来源与任务授权代理访问，不能让生成网页与控制台共享身份 cookie。产物保存源文件、构建包、截图和报告到内容存储；数据库保存引用与 hash。聊天中的 JSON/CSV 下载扩展为这些真实产物的入口。

### 记忆、评审与子代理

每次迭代带入固定需求、设计规范、当前任务清单、最近改动、未解决问题和少量近期交互；旧日志、源文件和图片通过引用按需读取。压缩按模型上下文占用触发，保留工具请求/结果配对。原始历史单独保留，摘要带来源范围和版本。

网页检查必须把 screenshot bytes/受控图片引用交给已验证支持视觉的模型；只把图片文件名返回给文本模型不能构成视觉检查。DOM 与构建日志用于功能和结构检查，不能替代截图审美判断。模型的视觉支持先做真实输入探测。

先以一个 Builder 打通闭环，再增加只读的视觉评审和功能评审子代理。每条反馈绑定 `artifactVersion + evidence + issue + acceptance`，包括严重度、位置、实际问题、修正建议及复验标准。子代理结果沿用已有轨迹关系，所有费用纳入任务预算。

一个候选版本只允许一个写入者。若后续需要多个编写子代理，分别给独立文件范围或隔离分支，由主代理合并并跑集成验收；禁止并发修改同一个共享目录。先复用现有单层委派，不为本场景增加无限递归。

## 迭代闭环与终止

```text
任务目标与验收清单
  → 读取当前版本和未解决问题
  → 选择本次有价值的修改
  → 文件修改、构建、启动预览
  → 浏览器功能检查 + 桌面/移动截图评审
  → 保存证据、版本、问题清单和检查点
  → 通过：保留可交付版本并结束
  → 未通过且有明确修正项：下一次迭代
  → 回退/无进展/预算到限/需要用户决策：保存状态并明确停止原因
```

基础规则：已满足要求可提前完成；有限次数重复失败后改变方法或停止；连续三次评审没有改善时重新检查问题定义，而不是自动微调颜色。保留“最近版本”和“最佳已验证版本”，最新版本退步时可回退。这个“三次”是首轮实验参数，不是已验证的最优值。

用户运行中补充要求时生成需求修订，在工具或迭代边界应用；已经取消的任务不能因评审、重试或子代理返回而复活。阶段完成给简短进度，具体过程继续走现有轨迹。

## 复杂任务基准

建议首个题目：为虚构数字艺术展制作完整作品网站。固定内容资料、合法素材包、功能清单与设计方向参考；需要有清晰的视觉概念、作品列表/详情、筛选、展示交互、访问信息、完整移动体验与键盘操作。交互不能只有外观，首版不连接真实支付或外部投稿。

阶段为：理解需求与设计参考 → 设计系统和首屏 → 全站结构与真实交互 → 桌面/移动视觉修正 → 动效、性能和无障碍 → 综合验收与交付。允许阶段内多次迭代，不机械分配固定次数。

区分三类实验：

| 实验 | 目的 | 判定 |
| --- | --- | --- |
| 自主任务，最多 80 个执行模型步骤 | 验证能否自行完成、检查和优化 | 允许提前达标，记录实际步数；不能为跑满而继续修改 |
| 80 步持续状态压力任务 | 验证检查点、约束保持、预算与恢复 | 用确有后续依赖的增量任务保证工作量；故障注入后状态和产物一致 |
| 80 个用户回合的会话回归 | 验证长期反馈理解与历史处理 | 独立测试，不与一个自主任务中的模型步骤混计 |

执行步骤计数包含主代理和执行子代理的实际模型调用，评审调用独立计数；重试也记录。总 Token/耗时预算覆盖执行、评审、压缩和重试，不能靠子代理绕开。80 是建议上限，不等于 80 次完整“构建—评审”循环。先跑 10 步标定消耗，再设 30/80 步档位的明确额度与截止时间。

每次实验固定模型标识、平台发布、Skills、提示词、初始代码、依赖锁文件、素材版本、工具版本、视口及浏览器版本；保存全部输入。对照组用同一基线和相同总预算，比较现有短运行、单代理闭环、带只读评审子代理的闭环。每档至少 3 次独立运行；记录模型采样与在线服务变化，固定输入不代表生成内容必然相同。

验收与报告：

- 硬检查：构建通过；关键操作实际完成；无未处理页面错误；桌面与移动无横向溢出；键盘可操作，减少动效设置有效；无严重无障碍问题。自动检查与人工检查各标明覆盖范围。
- 性能：固定环境与限制条件采样至少 3 次取中位数，记录 Lighthouse 实验室指标及原始报告。数值是工程门槛，不称为真实用户 Core Web Vitals 或获奖证据。
- 视觉：评审读取真实桌面/移动截图，按设计一致性、层级、排版、原创性、内容与交互逐项给证据；人对打乱顺序的初版和终版比较，判断改善和交付质量。评分口径在实验前固定。
- 稳定性：在模型响应后、工具执行后回执前、快照保存中等位置终止受控测试 worker；验证无重复文件操作、无状态丢失，预算仍累计，恢复后能取消。再测断网、模型限流、构建失败、子代理失败与停止。
- 长上下文：在任务开头写入不可丢失约束，后段用实际文件和页面检查是否仍满足；统计压缩次数、召回正确性与原始记录可追溯性。
- 成本与进展：记录总调用、步骤、工具失败、Token、耗时、每次有效改进及回退；只有价格来源明确时才计算费用，未知项保留未知。比较质量随预算的变化，不能只挑一个成功样例。
- 最终交付：源代码归档、可用预览、固定版本、桌面/移动截图、功能与性能报告、版本差异、未解决问题和完整轨迹。

## 实施顺序与完成标准

1. **网页执行的最小闭环。** 新建隔离项目，Agent 自己创建/修改文件、构建、启动预览、看到截图后修复一个真实问题。复用 native Workspace/Browser 工具，补图像和二进制产物通路。10 步以内任务验收；不能由平台开发者在外部代改网页冒充 Agent 完成。
2. **原生恢复兼容性实验与接入。** 用假模型和有幂等记录的文件工具测试 1.64.0 durable、内部 storage adapter、受控 kill/recover、双 worker 争抢和取消。核对工具 hooks、流适配和回放协议；通过后再进入正式长任务路径。
3. **任务状态、记忆和完成判定。** 提供累计预算、工作摘要、产物版本、真实验收和阶段续跑；配套 30 步任务与用户反馈修订测试。修复事件 10000 上限、64 步汇总以及长轨迹加载策略，容量按事件数和字节预算分别控制。
4. **评审子代理与 80 步基准。** 加入只读视觉/功能评审，运行上述对照实验和故障矩阵。只有执行可靠性和作品质量都出现有证据的改善，才考虑扩大默认任务预算和添加更多角色。

下一轮最具体的交付目标是第 1 项，并以第 2 项的小实验提前验证恢复路线；不先全面调整聊天布局或把 maxSteps 从 10 直接改成 80。
