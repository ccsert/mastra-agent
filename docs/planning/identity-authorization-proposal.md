# 客户、项目、应用与用户：身份授权讨论方案

日期：2026-09-07。状态：组织、调用上下文、共享与客户管理权限的产品基线已按用户持续推进授权收敛，正式结论见[明确客户、项目、业务应用与用户的授权关系](../../.scratch/agent-platform/issues/02-tenancy-and-delegation.md)的 Answer。本文中的具体操作清单、界面和协议仍为待实现设计。认证协议、统一身份中心交付与第三方身份接入由[身份中心决策](../../.scratch/agent-platform/issues/15-identity-center-boundary.md)处理。

## 已确认的前提

- 平台内使用与业务系统接入均属于首期能力，平台用户无需先注册一个外部业务应用才能使用 Agent。
- 业务应用支持统一认证，以及 AppID 与 AK/SK 应用验证两类入口；平台可以承担统一认证中心角色，也能接入第三方统一认证中心。
- 项目环境有默认资源位置，知识库和工具可指定其他位置；位置选择不能代替资源授权。
- 平台运营默认仅看运行状态，访问客户业务正文需要客户授予权限，托管内容同样适用。
- Skill 采用版本与资源范围授权，范围内可自主执行；工具自己的业务动作审批继续生效。

## 组织与资源关系工作基线

按前面给出的推荐继续采用：首期以独立客户组织作为租户边界，一个客户默认对应一个租户，部门或业务线通过项目组织资源，项目区分测试、生产等目标环境。保留客户与租户的概念区别，避免把客户资料编号直接当成租户身份；集团跨租户统一管理暂不作为本工作基线的交付项，如出现明确需求再调整。

| 对象 | 建议职责 | 关系与范围 |
| --- | --- | --- |
| 客户 | 平台服务的企业或组织 | 商业/组织关系，不直接作为每个接口的授权主体 |
| 租户 | 客户资源与权限的隔离边界 | 下设多个项目；跨租户访问不因同一集团、相同用户名或共用托管基础设施而自动开放 |
| 项目 | 团队或业务领域的协作空间 | 管理 Agent、工作流、Skill、工具、知识库和成员授权 |
| 环境 | 项目的发布与使用目的地，如测试、生产 | 绑定发布、默认 Runtime、存储和凭据；访问许可应明确环境范围 |
| 业务应用 | 以应用身份接入平台的外部系统 | 建议归属一个租户，可经授权使用多个项目中的资源；应用与项目不强制一一对应 |
| 用户身份与成员关系 | 识别人及其在租户、项目中的角色 | 同一个人可被授权加入多个项目；登录成功不自动成为所有项目成员 |
| Runtime / 连接器 | 在获准位置承接执行或连接 | 以执行方身份认证；部署位置或管理权限不赋予客户业务正文的通用读取权限 |

组织层级按上述推荐作为工作基线推进；表中的应用归属、授权表达和角色细节继续完善。环境可以复用物理基础设施，但测试环境的凭据或授权不能仅因共用 Runtime 就自动获得生产权限。平台托管 Runtime 如何隔离不同租户的工作负载由运行与隔离设计负责。

## 三种调用上下文工作基线

| 调用方式 | 识别的主体 | 适合的任务 | 建议的约束 |
| --- | --- | --- | --- |
| 平台用户直接使用 | 已认证用户、当前租户/项目/环境 | 平台聊天、文档上传、知识库使用、人工发起业务操作 | 依据用户和资源权限执行，不强制附带外部 AppID |
| 应用自身调用 | 已认证业务应用、目标资源与环境 | 定时报告、后台文档入库、系统自动任务 | 使用应用获得的服务权限，不伪造某位用户来填充审计字段 |
| 应用代表用户调用 | 业务应用与被可信识别的业务用户 | 内嵌聊天、基于用户权限的检索及业务操作 | 应用接入范围与用户可使用范围共同生效，同时审计两者 |

按前面给出的推荐继续采用三种调用上下文：平台用户直接使用、应用自身调用，以及应用代表可信用户调用。AK/SK 接入中的服务任务与用户委托分别识别权限和审计上下文。此处记录按用户持续推进授权采用的工作基线，不将其描述成用户曾对选项作出逐项书面答复。

应用代表用户调用时，建议先为业务后端建立获准的身份委托关系，限定其能够代表的用户来源与租户范围，再交换面向具体用途的受限会话凭据。不能仅因请求体出现 userId 就认定可信；应用拥有 AK/SK 也不应自动获得冒用租户内任意用户的能力。具体证明、交换协议与重放防护由身份中心和接入契约验证。

第三方用户身份建议按身份来源与该来源内的稳定标识映射，不能只凭相同用户名或邮箱合并帐号。可以为外部用户建立主体映射，无需因此为每个人新增一套本地密码；自动建档是否同时获得成员资格、跨应用映射能否复用，仍需明确规则。

## 一次调用的权限判断建议

先识别实际用户/应用及其允许的上下文，再检查目标环境与发布资源是否可用，最后按发布的能力授权、数据政策和业务系统权限执行。

```text
调用主体允许的范围
∩ 已发布 Agent / 工作流获准使用的能力
∩ 目标资源与环境的授权
∩ 内容传输、模型处理和执行限制
∩ 业务系统实际允许的操作与数据范围
```

这是权限设计的概念表达，并非已经实现的策略引擎。应用自身调用按应用的服务权限判断；代表用户调用还需限制到该用户获准的范围。平台内调用使用用户上下文，不人为引入一个拥有额外权限的外部应用身份。

允许使用 Agent 与允许下载知识库原文、读取 Secret、直接调用底层工具是不同操作。资源授权可以允许“通过指定 Agent 使用”，同时限制原始内容下载或直接接口访问；不能为了运行 Agent 就向终端用户发放底层长期凭据。检索结果和工具返回的数据范围应在进入模型前按实际调用上下文落实。

业务系统实际执行身份需明确选择应用服务帐号或用户委托身份。平台识别了用户，不等于订单系统已接受该用户的身份；如果使用应用服务帐号，工具契约仍需约束其可操作的数据范围，并同时记录发起用户与实际执行帐号。具体身份映射和工具能力由工具治理决策细化。

## 管理权限与内容权限建议

角色名称暂作为讨论模板，不代表首期角色清单已批准。

| 权限类别 | 可包含的操作 | 需要分别表达的能力 |
| --- | --- | --- |
| 租户管理 | 管理成员、项目、身份来源与应用接入 | 身份管理、授权管理和正文访问分别授予 |
| 项目建设 | 编辑 Agent/工作流、上传 Skill、登记工具与知识库 | 编辑草稿、发布到环境、授予执行资源范围分别表达 |
| 发布与授权 | 发布指定环境版本、批准能力绑定及资源范围 | 不能把拥有画布编辑权直接等同于拥有生产工具授权权 |
| 业务使用 | 使用获准 Agent/工作流、提供输入和读取自己的产物 | 调用能力、查看会话、下载原文与共享历史分别表达 |
| 内容审阅 | 在客户授予范围内查看会话、文档或运行正文 | 明确客户、项目、对象范围与用途，保留访问审计 |
| 平台运营 | 查看运行状态和维护平台服务 | 已确认：客户正文访问需要客户授予权限，托管内容同样适用 |

建议以角色模板降低配置成本，以资源、操作和环境范围表达实际权限。内置角色、自定义角色及授权界面的具体交付深度在后续规格中细化；已采用客户项目管理与业务正文权限分开的基线。平台资源授权由平台表达，外部身份中心的组织或角色声明需要经过映射才能成为平台权限。

## 已采用的资源、会话与正文权限基线

### 资源默认归项目，跨项目显式授权

Agent、工作流、Skill、工具和知识库默认归属创建它们的项目。在同一租户内，通过显式授权允许其他项目或业务应用使用；跨租户共享不由这一规则开放。资源负责人和授权管理角色的具体权限清单在后续规格中细化。

共享许可需区分查看目录/定义、使用已发布能力、编辑、发布、下载原始内容与再次授权。使用方获得某项能力，不自动获得该能力所有内部资源的管理权限。例如业务应用可以使用订单助手，但不能据此下载整个知识库或读出工具凭据。

共享采用资源引用与授权关系，已发布运行继续固定依赖版本；撤销或收窄授权不会通过复制资源被绕过。共享私有知识库或工具也不自动搬迁数据，原有位置、传输和模型处理政策继续生效。资源所有方的控制和使用方的授权共同约束实际调用。

### 会话按实际主体与应用入口隔离

默认在租户、项目、环境范围内，按应用入口与会话所有者隔离历史。同一个人在订单系统与客服系统使用同一个 Agent，默认拥有独立会话；平台内使用也有自己的入口范围，并不要求注册一个外部业务应用。

入口与主体由服务端根据可信认证上下文识别，不能由浏览器随意传入另一个 AppID、用户标识或会话标识完成切换。应用服务任务的运行归属应用服务主体，不虚构业务用户；谁能查看其产物由对应内容权限决定。

需要连续使用或共享时，授予指定会话的访问权限。查看历史、继续对话、下载附件和分享给第三方应用分别表达；共享某个 Agent 定义不会批量开放其所有会话。共享还须满足内容传输政策，不自动合并用户身份或改变既有运行、存储位置。

### 客户管理权限与正文权限分开

客户项目管理员的管理权限与内容访问权限分开；查看他人会话、文档及工具结果正文需要具备相应内容访问权限。管理员本人的会话和已授权业务资源按普通使用权限访问，管理操作的具体清单由角色设计落实。

租户可以为内容审阅、客服主管或项目负责人配置长期有效的范围授权，也可以配置临时授权；这不是逐条消息审批。谁能授予内容权限、是否允许给自己授权及授权审计在身份规则中明确。平台运营人员仍受已经确认的客户授权边界约束，不能自行代替客户授予自己正文权限。

### 讨论案例的预期差异

| 场景 | 按本轮推荐方案应发生什么 |
| --- | --- |
| 项目 B 使用项目 A 的订单助手 | 先有同租户的资源使用授权；B 不因此获得 A 的编辑、发布或全部内容权限 |
| 同一用户在两个业务系统访问同一 Agent | 会话默认分别保存；只有获准共享的会话可以被另一入口查看或继续 |
| 客户项目管理员排查某位用户的失败运行 | 默认能看运行状态；要查看该用户输入或完整工具结果，需已有或取得内容访问权限 |
| 业务应用拿到另一应用的会话标识 | 服务端仍按入口、实际主体和内容权限校验，标识本身不能授予访问 |
| 私有知识库被共享给托管 Agent | 只在获准的检索、传输与模型处理范围内使用，知识库不会因此复制到平台 |

本节的默认行为已在具体推荐后按用户“可以持续推进”的授权采用。具体角色命名、权限操作清单与接口错误码继续设计验证。

## 用两个业务系统检查默认行为

假设同一客户在一个项目中发布“订单助手”，由订单系统和客服系统复用。两位使用者分别只负责不同区域的订单。

| 情况 | 已采用的产品行为 | 后续实现契约 |
| --- | --- | --- |
| 两个系统获准使用同一个 Agent | 复用发布能力，每次运行保留应用及用户上下文；跨项目使用须显式授权 | 授权操作、版本引用及审计字段 |
| 同一个人在两个系统打开聊天 | 用户身份可在可信映射下对应同一人；会话默认按应用入口隔离，指定会话可显式共享 | 分别落实查看、继续与附件权限及会话绑定 |
| 两位用户执行相同查询 | 在获准的数据范围内检索和调用工具，不能因复用 Agent 扩大可见订单范围 | 可信用户映射与数据范围校验的具体契约 |
| 订单系统执行夜间汇总 | 使用明确授权的应用服务权限执行，历史归属服务任务 | 哪些客户角色能查看和管理服务任务历史 |
| 测试应用请求生产 Agent | 无生产环境授权时拒绝 | 环境授权是否使用独立应用凭据或受限交换凭据，由接入契约决定 |
| 应用只有 Agent 使用权 | 可在许可范围内使用能力，不自动获得知识库原文下载或 Secret 读取权限 | 资源的操作权限模板 |
| 应用被停用或用户离开项目 | 后续调用按最新可用权限与会话有效性判断；进行中任务、缓存与离线行为另有契约 | 撤销时效与历史归属由身份、内容和恢复契约细化 |
| 平台运维排查异常 | 默认通过运行状态排查；取得客户授予的内容权限后才可查看正文 | 授权角色和访问审计细节 |

共享 Agent 定义、共享底层资源和共享会话正文分别授权。会话位置继续遵循已确认的托管/私有配置；修改入口、显示名称或登录帐号映射不会自动迁移、合并旧会话。

## 当前基线与后续实现契约

已按具体推荐继续采用“独立客户组织对应租户 → 多项目 → 目标环境”，以及应用自身任务与可信用户委托两种 AK/SK 调用模式。本轮不重复询问这两个基础方案。

资源默认项目私有并支持显式跨项目授权、跨应用会话默认隔离及客户管理员需要内容访问权限也已采用。身份决策已关闭，后续补齐可信身份映射、权限操作清单、角色配置、授权审计与撤销行为。

具体认证协议与身份服务选型留给身份中心决策；平台资源权限及角色配置界面由后续平台规格落实。这些授权能力尚未实现，不能当作 Mastra、FlowGram 或 assistant-ui 自动提供。
