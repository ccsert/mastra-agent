# Skill 包从导入到执行：首期讨论方案

日期：2026-09-07。状态：包与执行授权产品契约已收敛，导入及实现细则待完善。正式结论见[明确 Skill 包、授权与执行边界](../../.scratch/agent-platform/issues/03-skill-contract.md)的 Answer，技术承接见[Skill 运行架构基线](skill-runtime-architecture.md)。本文保留讨论方案与细则建议，整体实施规格尚未批准，也不代表已实现或验证。

## 已确认的输入

用户要求保留独立 Agent、知识库和工作流能力；Skill 采用标准 Agent Skills 格式，允许上传压缩包并校验规范。Agent 使用 Skill 无需先建立工作流；工作流中的 Agent 节点也可使用绑定的 Skill。

用户已选择“版本与范围授权后自主执行”：首期允许包内脚本在选定 Runtime 的隔离环境中，按获准的 Skill 版本及资源范围自主执行。用户后续明确平台也要存储业务内容并直接操作业务系统，因此相同执行契约适用于平台托管与客户私有 Runtime。正式讨论记录保留在上述决策票据中。

用户随后授权继续推进语言与依赖建议：首期以 Node.js、Python、Bash 为基线，依赖在发布或执行环境准备阶段固定，执行时复用准备完成的环境。

官方标准以 Skill 目录和 SKILL.md 为核心，可包含资源与脚本。格式本身不规定平台上传、授权和隔离策略。除上文已确认的方向外，下文细则仍为平台建议；标准依据见[已完成的规范研究](../research/agent-skills-standard-2026-09-07.md)与[官方规范](https://agentskills.io/specification)。

## 建议的首期行为

| 环节 | 建议行为 | 可观察的结果 |
| --- | --- | --- |
| 上传 | 首期接收 ZIP，一个归档包含一个 Skill；支持文件直接位于归档根部，或位于唯一外层 Skill 目录 | 展示识别到的包名、说明、文件清单和导入结果 |
| 解包 | 在受限临时区解包，限制体积与文件数量，拒绝越界路径、重复路径和符号链接；根目录模式按合法 name 建立 Skill 目录，已有外层目录须符合名称匹配规则 | 不合法归档返回具体路径与原因，原始上传文件不会直接进入执行目录 |
| 格式校验 | 检查标准强制项；编写建议作为提示；平台的归档限制独立展示 | 用户能区分格式错误、平台限制与非阻断建议 |
| 登记版本 | 分配平台资源标识，保存原始包与内容摘要；同名处理遵循资源作用域，不以压缩文件名代替 Skill 身份 | 草稿可修正；已经发布的包内容固定，修改形成新版本 |
| 绑定使用 | 独立 Agent 或工作流中的 Agent 节点引用具体 Skill 版本 | 用户能够查看某个 Agent 使用的 Skill 版本及授权范围 |
| 准备运行环境 | 在执行前准备并固定依赖；缺失依赖时报告环境不满足 | 运行中的 Agent 不自行联网安装未知依赖 |
| 发布授权 | 具备授权权限的人批准具体 Skill 版本、可使用方、目标环境及可执行操作 | 该版本在获准范围内可自主执行；超出范围时明确拒绝，扩权走新的授权 |
| 运行 | 选定 Runtime 按最终授权在隔离环境中执行，关联当前运行的输入、输出和审计 | 能追踪使用的版本、脚本、调用资源及结果 |

上传仅创建待使用的资源；运行许可由平台管理。无需为了登记平台版本或授权而要求用户改造标准包。标准包内的 metadata、allowed-tools 等输入不直接产生平台授权。

归档类型、单包限制及上述路径策略是本方案的首期建议；具体体积、文件数和执行预算在规模与隔离设计中确定。平台可保存包体、输入与执行产物，也支持客户私有存储；客户私有内容默认保留在私网，按客户政策传输。项目环境默认位置以及知识库/工具可指定其他位置已确认；Skill 跨环境分发及界面正文访问规则仍由数据决策细化。

## 已确认的授权模式与建议的资源细则

**已确认：按版本和范围授权，授权范围内由 Agent 自主执行。** 下列默认资源规则仍待收敛。

- 文件：只接触本次运行提供的输入和工作目录，输出登记为本次运行的产物；宿主目录不默认挂载。
- 网络：默认不开放任意网络访问；业务系统操作优先经已授权工具进行，需要直接访问的目标单独列入许可范围。
- 凭据：引用平台管理的凭据或授权工具；不要求把长期 Secret 写进 Skill 包。
- 依赖：在发布或环境准备阶段固定；执行过程中新增系统能力、安装依赖或扩大网络范围需要重新准备与授权。
- 预算：运行受时间、资源和输出大小约束；具体阈值后续根据样例及运行规模确定。

最终执行范围由 Skill 版本授权、Agent/应用授权和 Runtime 环境限制共同约束；若调用携带业务用户身份，还应受该用户授权约束。用户委托的接入方式在身份决策中确认。

普通 Skill 脚本的执行授权与业务动作审批分别表达：例如调用“提交付款”工具是否需要每次批准，由该工具和业务流程的策略决定。允许脚本运行不自动取消这些审批。

## 用一个场景检查理解

业务团队上传“生成月度报表”Skill。它读取本次上传的表格，调用已注册的订单查询工具，并生成可下载的报表。

按推荐方案，首次发布时批准这个 Skill 版本使用订单查询工具、运行内文件与所需依赖。后续用户调用时，Agent 可在这些范围内自行执行，无需逐次批准每个脚本。若新的版本需要写回业务系统、读取额外目录或访问新的地址，则需要新的授权。

原包缺少规范要求的字段，应在导入时反馈；运行时缺少某个依赖，应反馈环境不满足；请求超出授权，应反馈所缺权限。三类问题分别处理。

## 首期运行环境基线

用户在收到具体建议后同意继续推进，采用以下基线：

1. 提供平台管理的 Node.js、Python 与 Bash 环境。具体解释器版本随环境版本固定；客户自带任意环境尚未纳入这一基线。
2. 在发布或执行环境准备阶段固定依赖，执行时复用已准备环境。运行中缺失依赖应返回可诊断的错误，通过新的环境准备完成修正。

依赖准备可能执行第三方安装代码，也应与管理服务、执行服务进程及其他运行的数据隔离。准备后的环境与 Skill 内容分别固定版本；这项约束不意味着必须每个 Skill 独占一个镜像。

后续还需细化资源范围和导入契约；角色权限、客户数据驻留、授权撤销与断网行为，以及发布版本跨重启的恢复规则，分别由身份、数据、运行恢复和发布决策承接。
