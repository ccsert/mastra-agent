# 首期身份中心交付方案

日期：2026-09-07。对应[身份中心交付边界](../../.scratch/agent-platform/issues/15-identity-center-boundary.md)。既有租户/项目/环境、应用任务和可信用户委托基线不重新讨论；下文给出待审阅的交付范围。Keycloak 为研究推荐的原型候选，尚未部署或选定生产拓扑。

## 建议的职责划分

**平台提供统一认证产品能力，底层复用成熟身份服务；资源、会话与内容授权由平台掌握。** 集中平台侧部署身份服务，客户私有 Runtime 不因此必须部署完整 IdP。

| 部分 | 首期建议交付 | 与平台主体的衔接 |
| --- | --- | --- |
| 平台自有身份 | 租户受控邀请/建档、登录退出、密码恢复与 MFA，具体界面复用并定制身份服务 | 本地用户绑定平台主体，成员资格由项目授权决定 |
| 第三方认证中心 | 优先通过 OIDC 联邦；能由身份服务适配的 SAML/LDAP 保留接入能力，按首个客户需求验证 | 以受信 issuer + 稳定 subject 建立映射，不凭同邮箱合并 |
| 向业务系统提供认证 | 为业务应用登记 OIDC client、redirect URI、允许来源和相应用途 | OIDC client 与平台 AppID 显式关联；不是同一个凭据对象 |
| 应用自身任务 | AppID/AK/SK 建立应用身份，取得受限服务调用上下文 | 审计为应用，不虚构人类用户 |
| 应用代表用户 | 同时验证应用身份、许可的用户证明来源及用户权限 | 保留 app、user、身份来源和实际业务工具执行主体 |
| 平台资源授权 | 租户/项目/环境/资源/操作/正文与会话入口判断 | 身份服务角色只有经映射才成为平台授权，不绕过客户内容许可 |

首期不自行实现密码存储、OAuth 授权服务器和 MFA 协议。建议暂不承诺完整的 HR/组织目录双向同步、任意字段映射编程平台或集团跨租户总管理；这些若是首客必需项，需要单独加入验收。本地帐号与邀请、MFA、密码恢复等交付范围是本方案建议，尚未由用户逐项选择。

## 选择 Keycloak 的依据与验证边界

官方固定源码表明 Keycloak 26.7.3 的 Organizations、标准 Token Exchange V2、JWT Authorization Grant 默认支持，显式 Delegation 与 Identity Assertion JWT 为实验功能。建议原型采用前者可验证的协议能力，不将后者作为产品可信委托的必要条件。[固定功能状态](https://github.com/keycloak/keycloak/blob/6d238b6558037085cc25c915893c3d301a80243e/common/src/main/java/org/keycloak/common/Profile.java)。

对比、许可证据、其他候选和部署事实集中在[统一身份服务研究](../research/identity-provider-options-2026-09-07.md)，本方案不复制一套选型表。工程推荐不等于全部官方功能均进入首期。

原型可用两个 Realm 检验发行者隔离。生产一租户一 Realm 或共享 Realm + Organizations 的选择保留到身份规模、客户定制、帐号共享与运维成本明确后；不能由两个测试 Realm 自动推导生产拓扑。

## 三种调用的共同执行上下文

```text
已认证平台用户 ──────────────┐
已认证应用（服务任务）────────┼─> 平台授权 ─> 受限执行上下文 ─> Runtime / 工具
已认证应用 + 可信用户证明 ────┘
```

服务端生成的执行上下文至少关联租户、项目、环境、发起应用或平台入口、用户主体（存在时）、可用资源与操作、运行标识、授权修订及有效边界。这是领域契约，不是已经发布的 token schema。

有用户委托时，权限取应用允许范围、用户允许范围、资源规则、当前动作政策的交集；第三方提交的 `userId` 只是请求参数，不能自动成为已证明身份。外部身份映射建立成功也不自动获得项目成员资格。下游业务系统另决定接受服务账户还是用户委托，平台把自身 userId 传过去不能代替下游鉴权。

建议采用显式受信发行者与用户绑定；平台的 AK/SK 不直接替代 IdP 的 OAuth client secret。应用签名/换发协议、短期凭据格式、重放防护、吊销检查和轮换窗口由 API 接入契约固定，并以生成的 OpenAPI SDK 提供接口，不维护第二套手写 HTTP 客户端方法。

## React、UI SDK 与 iframe

控制台保持 React + Vite，与 IdP 使用标准登录跳转。浏览器不持有长期 SK 或 confidential client secret；SPA Code + PKCE 与 BFF 会话两种实现需结合嵌入、跨站 Cookie 和运行域路由验证后定型。Keycloak 官方说明浏览器第三方 Cookie 限制会影响 silent SSO 与登出检测，不能把 iframe 静默登录当作唯一可用路径。[官方 JS adapter](https://www.keycloak.org/securing-apps/javascript-adapter)。

建议业务后端取得绑定应用、用户、允许来源及用途的短期嵌入凭据，再与组件建立受限会话。需要验证 origin、audience、过期与续期、宿主退出、跨应用会话 ID 以及 iframe 握手重放。宿主页面拥有用户可见内容的事实要与客户内容政策一致；iframe 本身不创造新的数据授权。

具体握手、组件 API 与凭据传递方式交给[API/UI 接入契约](../../.scratch/agent-platform/issues/12-api-ui-embedding-contract.md)，不在这里另写一套冲突协议。

## 身份生命周期的建议语义

| 事件 | 建议的产品行为 | 还需验证的机制 |
| --- | --- | --- |
| 外部用户首次登录 | 创建或匹配受信主体链接；无项目成员资格则不自动开放资源 | 首次登录流程、受控邀请、身份冲突处理 |
| 同邮箱来自另一 IdP | 作为独立外部身份处理；只有可信的显式流程可关联 | 防止邮箱猜测合并与跨租户串号 |
| 用户离职/应用停用 | 拒绝新调用、失效受影响会话；历史按原归属保留并继续鉴权 | 事件同步、在线校验、缓存与已发凭据的失效时限 |
| 外部 IdP 不可用 | 新登录清晰失败；已存在会话按其有效期和平台撤销策略处理 | 超时、错误页面、依赖恢复；不自动降级到弱认证 |
| 控制面与私网断连 | 按已确定的运行授权期限和恢复契约判断，不能接受无期限离线凭据 | Runtime 的策略租约、时钟偏差与重连同步 |
| 平台运营排障 | 默认只有状态；正文访问仍需客户许可且记录使用 | 管理入口和正文下载路径均执行授权 |

这些事件的秒级时限仍需与 Runtime 恢复、内容策略协同，不由身份服务 access token 的 TTL 单独决定。首期是否启用组织目录持续同步、何种停用事件可用，取决于首客身份源。

## 原型的通过门槛

先用固定版本身份服务验证自有登录、外部 OIDC 联邦、应用任务和受信用户委托，再加 React/iframe 浏览器证据。正反例至少覆盖错误 issuer/audience、过期与重复断言、相同邮箱不同来源、应用与用户权限交集、错租户/环境、停用后的行为。详细清单复用[研究中的最小验证](../research/identity-provider-options-2026-09-07.md#最小验证清单)。

本方案等待首期身份产品范围审阅；当前身份中心决策保持 claimed。研究已结束，运行验证尚未启动。
